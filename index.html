How we calculate
Method and accuracy reportHeld-out accuracy on our measured runs, measured hardware vs datasheet, and the tested price cap: read the report.
Fine-tune throughputFrom our own benchmark runs ( fine-tune runs on GPUs: transformers + PEFT, each model's real architecture, full-length sequences). The speed comes from the best source available, in this order: our runs of this model at this GPU count; our 1-GPU runs of it times the measured multi-GPU efficiency; another GPU's runs of it times the speed ratio of the two GPUs on models both ran; for a GPU we never ran, the closest measured GPU scaled by datasheet speed. The card and the Performance tab say which. Speed depends on tokens per GPU per step (batch x processed length), fitted per GPU on our runs; a setup outside the measured range is scaled from the nearest run and labelled so. Each setting is a measured ratio against the same run with base settings (checkpointing off, eager attention, LoRA rank, optimizer, QLoRA, DPO, MoE). Full fine-tune is measured only up to 1.7B, where it is faster than LoRA; beyond twice that size it uses the weight-gradient FLOP ratio and says it is not measured. Sequences longer than any measured run add attention FLOPs. Multi-GPU efficiency is fitted on our 2, 4 and 8 GPU runs against the same run on 1 GPU.
Price capSet per quote by a hierarchical Bayesian model of the calculator's own held-out errors: each GPU and model gets its own error level, pooled with the rest, and small models get more room. A GPU we measured gets a tight cap (about x1.2 to x1.35 at 90%); a GPU we have not measured gets about x1.5. Tested nested, with the scored GPU or setup never in the fit: the 90% cap held for held-out runs on measured GPUs and on unmeasured ones.
MemoryWeights = params x precision bytes (QLoRA NF4 about 0.55). KV cache = 2 x KV heads x head dim x tokens x layers (latent for MLA models), reduced by sliding windows. Training adds gradients (2 bytes per trained param), optimizer state (AdamW 8, Lion 4, SGD 4 bytes, a quarter with 8-bit), fp32 master weights for full fine-tune unless pure 16-bit, activations (shrunk by gradient checkpointing, plus attention scores without Flash Attention) and an fp32 logits buffer (smaller with fused kernels). Full fine-tune lands at 16 bytes per param, matching apxml.
InferenceWhere we ran the exact setup with vLLM ( serving runs), the page uses that run. Otherwise a decode step takes the longer of reading the weights plus every sequence's KV cache at 74.5% of bandwidth (56% for INT4) and its compute (decode tokens at 16% of peak, the prompts feeding them at 58%), plus 1.4 ms per step; tensor parallel adds two all-reduces per layer. First token is 7.5 ms plus the prompt's compute at 58% of peak, attention included. That roofline is then corrected with our vLLM runs on the same GPU (per-token time, first-token time and how first-token time grows with users, fitted only on runs where every user fitted in KV memory). A GPU with no vLLM runs borrows the closest measured GPU's correction and says so. Total throughput counts each user's wait for the first token, as vllm bench serve measures it. A model that fits on one GPU is served by replicas; tensor parallel is used inside a box and pipeline stages only across boxes (not measured). Max users is set by KV memory at 90% of VRAM.
RatesOur invoiced rate where we have one: A100 $1.425 (Gcore commits) and H100 $2.60 (Gcore PAYG). Others use a public on-demand list price: RunPod Secure Cloud (13 Sep 2026), Lambda, or the Vast index. Apple machines are bought, not rented, so they have no hourly rate. GPUs with no rate in these sources show time and speed only. Costs add our 10% overhead and no margin.
Models and GPUs412 models with architecture (layers, KV heads, head dim, experts, sliding windows, MLA) from each model's config.json on Hugging Face and exact parameter counts from its weights. 44 GPUs across NVIDIA, AMD, Apple and Intel, plus a custom GPU, with vendor datasheet specs (dense BF16, no sparsity).
